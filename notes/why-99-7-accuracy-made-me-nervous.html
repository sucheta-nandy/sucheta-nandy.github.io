FIELD NOTE 01 · MODEL EVALUATION

Why 99.7% Accuracy Made Me Nervous

The score was excellent. The questions it raised were better.

By Sucheta Nandy 8 min read November 2026
99.7%
→
SIGNALorLEAKAGE?

There are numbers that make a machine-learning project look good, and numbers that make you look at the project again. For me, 99.7% test accuracy was both.

I had built a multiclass model to predict whether an Uber booking would be completed, cancelled by the customer, cancelled by the driver, left incomplete, or fail because no driver was found. The pipeline compared logistic regression, a decision tree, random forest, and XGBoost. It handled imbalance with SMOTE and reported several metrics. On paper, this was exactly the sort of result I should celebrate.

But a model that is almost never wrong is making a claim about the world: that the outcome is almost completely knowable from the inputs. Ride marketplaces are noisy. Supply changes. People change their minds. Traffic exists. A near-perfect score did not match the messiness of the system I thought I was modeling.

When a metric feels more orderly than the world it describes, audit the experiment before admiring the model.

The prediction boundary comes first

The most important question was not which algorithm won. It was: At exactly what moment is this prediction supposed to be made?

If the goal is to predict booking status when a ride is requested, the model may use information available at request time: location, hour, vehicle type, perhaps current supply. It cannot use fields created after the ride has progressed. Payment method availability, fare values, driver or customer ratings, cancellation metadata, and incomplete-ride flags may all contain pieces of the answer.

My pipeline explicitly removed cancellation reasons and several obvious outcome fields. That was good—but not sufficient. Some remaining fields could still be lifecycle artifacts. A missing fare filled differently for cancelled bookings, for example, can become a tidy numerical shortcut for the target. The model is not cheating. It is doing exactly what I asked: finding the easiest predictive pattern in the table.

THE FEATURE TEST

Could this value exist, in this form, at the instant the prediction is requested?

If the answer is no, it does not belong in the feature set.

A test set can quietly become a validation set

I also found a subtler problem in the evaluation loop. Several model configurations were compared using performance on the same test split, and the best configuration was selected from those results. Once a test set influences model choice, it is no longer an untouched test. It has become part of the tuning process.

Nothing has to be copied from the test rows into training for this to matter. Repeatedly asking “Which version does best here?” transfers information through decisions. The final estimate becomes optimistic because the experiment has adapted to the supposed final exam.

Random is not always realistic

A stratified random split preserves class proportions, but it may not represent deployment. If a model will predict future bookings, a temporal split is the more honest simulation: train on earlier periods, validate on a later window, and test on the latest untouched window. That design exposes changes in demand, supply, behavior, and data collection that a random split can blur together.

The right split is not a generic best practice. It is a miniature version of the future the model will face.

How I would rebuild the evaluation

  1. 01
    Write the prediction contract. Define the decision, prediction timestamp, target window, and data available at that moment.
  2. 02
    Build an availability-aware feature list. Remove post-outcome fields and audit missingness itself as a potential label proxy.
  3. 03
    Separate tuning from testing. Use training and validation data for model selection; touch the final test window once.
  4. 04
    Match the split to deployment. Prefer a time-based holdout when the model is expected to generalize forward.
  5. 05
    Measure the failures that matter. Report macro F1, per-class recall, confusion patterns, calibration, and a simple baseline—not accuracy alone.

The better result may be a lower number

After removing shortcuts and making the evaluation more realistic, performance will probably drop. That is not a failed project. It is the point at which the metric begins to mean what we thought it meant.

This changed the way I talk about machine learning work. I am still interested in stronger models, but I am more interested in whether the system earned the right to make its claim. A trustworthy 78% can be far more valuable than a mysterious 99.7%.

The first version of this project gave me a high score. Auditing it gave me something better: a sharper definition of prediction, a more honest experiment, and a question I now carry into every model review— what did the system know, and when did it know it?

THE TAKEAWAY

The job is not to produce the largest metric. It is to produce a metric that survives the next question.
